## Architecture rules

- Dashboard cards are presentation only. ResumeScoreCard (random pending action, rank progress, reward labels from the latest review), DashboardProgressCards (one merged card titled Career whose ring, progress and rank come from GameProvider) and the top-bar QuestMenu (capped daily/weekly lists) read GameProvider and only navigate — they never award XP, create quests, or change resets. Why: gamification must reflect the existing Resume Lab and quest workflow, not invent leaderboards or unlocks.
- Featured quest display titles use the browser-safe quest-titles helper and always render as two lines while preserving full saved titles. Why: concise card copy must not rewrite user quests or require data migrations.
- Max poses come from `MAX_POSES` with uploaded mascot images as CDN asset pointers (sign-in shares the same wave source); shared motion lives in global CSS and AppShell's reduced-motion-aware MotionConfig, and stateful encouragement stays in frontend components. Why: one art mapping and one motion system keep polish from touching persistence or the interview and resume flows.
- JobMaxxing persists game state (profile, XP, quests, resume reviews, interview sessions) in Neon Postgres through the Lovable connector gateway, not Lovable Cloud. Keep reads and writes in `createServerFn` handlers (`src/lib/devup.functions.ts`) using the helpers in `src/lib/neon.server.ts`, never call the gateway from browser code, never store state in localStorage, and run schema changes once through the gateway or Neon's SQL editor rather than at request time. Why: the user chose Neon as the backend, and request-time DDL multiplies one migration into thousands of statements.
- Mock interview agents (job parser, question, grader) sit behind server-only adapters in `src/lib/interview/agents.server.ts`; each uses its Raia agent when its secret env var is set and a built-in fallback otherwise, and voice goes through the `VoiceAgent` interface in `src/lib/interview/voice.ts`. Why: agents are added later without touching the UI flow.
- Accounts are email + password in Neon (`devup_user`, PBKDF2 hashes) with httpOnly cookie sessions (`devup_session`, SHA-256 of the token); private server functions scope by `requireUser()` from `src/lib/auth.server.ts`, and `startSession` sweeps expired sessions and keeps each user's newest few in one transaction. Why: Lovable Cloud auth is unavailable, OAuth can land on the same session table, and with no cron sign-in is the natural prune point.
- One Raia conversation runs each live interview (Question agent, `/external/conversations` + `/messages`), each spoken line voiced by ElevenLabs TTS on the server and candidate speech captured by browser speech recognition, with any failure falling back to the planned questions and browser voice. Why: the agent keeps context across turns while the interview never dead-ends.
- Featured-quest card layouts (Max/backdrop offsets and sizes per quest type) live in Neon `devup_featured_layout` via `src/lib/layout.functions.ts`; only the editor email set there may save. Why: one designer tunes the cards for everyone without code changes.
- Resume grading uploads the original file (PDF/image) to the Raia Resume Agent via `/external/prompts/upload-url` + `files` (pdfjs text is only a fallback); the agent's instructions and output JSON schema live in Raia and must match `normalizeReview` in `src/lib/interview/agents.server.ts`. Every scan or editor save is a `devup_resume_version` row, each grade a `devup_resume_review` linked by `version_id`, and one-time XP milestones use `milestone:*` reasons on `devup_xp_event` (unique index). Why: version history, scanned resumes and idempotent XP need the original file and stable line ids.
- Never `order by id` after aliasing `id::text as id` — it sorts as text; qualify the table column. Why: '9' > '11' showed stale grades.
- The dashboard's featured quest card fills the viewport (`min-h-[calc(100svh_-_4rem)]`) and `AppShell` drops its page padding only on `/`; the greeting, quick-route shortcuts and progress cards live below the fold in their own padded container. Uploaded CDN scene pointers render as full-inset cover pictures with portrait sources on mobile, behind text and Max, who sits on the card's horizontal center line at every width. Why: artwork must fill the screen rather than a right-side partition, and one mascot placement reads as one consistent character across quest types.
- Quest reset countdowns derive from `src/lib/reset-times.ts` (`nextDailyReset` = next 00:00 UTC, `nextWeeklyReset` = next Monday 00:00 UTC) and render only after hydration. Why: they must match the server's `date_trunc('day'|'week')` flip exactly, and a server-rendered time would hydration-mismatch.
